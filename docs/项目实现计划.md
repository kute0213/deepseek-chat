## 1. 目标与交付物

构建一个可部署的 DeepSeek 网页版：

1. **前端完全沿用官方 deepseek-chat-demo 的界面与交互**（React 18 + TypeScript + rspack），不自行重写 UI；只替换「数据存取层」与「API 调用层」。
2. **后端 PHP + MySQL**：账号系统、API Key 服务端保管、会话与消息持久化、DeepSeek 请求转发、附件/语音代理、历史导入导出。
3. **完整管理后台**：仪表盘、用户、会话、附件、管理员、站点设置、公告、日志、导出。
4. **安装向导 `install.php`**：配置 MySQL 连接、初始化表结构、创建管理员。
5. **雪花算法**：用户、会话、消息、令牌、日志统一使用同一套雪花 ID 生成函数，全局不重复（含并发与进程重启）。
6. **完整支持官方功能**：多会话/分支/重新生成/编辑、流式回答、深度思考、联网搜索、链接阅读、标题生成、附件、语音输入与朗读、Markdown/公式/Mermaid、中英文、主题、历史导入导出。

交付目录包含：可运行源码、前端构建产物、`README.md`、本计划文档。

## 2. 关键决策

| 决策点 | 方案 | 理由 |
| --- | --- | --- |
| 服务端代码位置 | 直接放仓库根目录（`index.php`、`app/`、`admin/`、`config/`、`database/`、`storage/`） | 符合要求，不为了分层强行套 `server/`，结构直观 |
| 前后端分离 | 前端源码独立在 `frontend/`，只通过 `/api/*` 契约访问后端；默认同源部署，也可拆域 | 结构清晰，互不混杂；后续可独立部署 |
| 官方 Demo 位置 | `scripts/deepseek-demo/`，`/scripts/` 整体加入 `.gitignore` | 只作参考与复制来源，不进仓库、不上 GitHub、不保存 Git 历史 |
| 前端来源 | 从 `scripts/deepseek-demo/` 复制源码到 `frontend/`，保留组件、样式、i18n、Markdown、语音全部代码 | 满足「完全按照这个风格/直接抄」 |
| 数据存储 | 会话以官方 `Session` JSON 整体存 MySQL，附件元数据单独表、原件存服务器磁盘 | 与官方 IndexedDB 结构一一对应，分支/块/用量零改造 |
| 对话链路 | 浏览器 → PHP `/api/deepseek/messages` → DeepSeek Anthropic 兼容接口，PHP 透传 SSE | 满足「服务端转发」，API Key 不下发浏览器 |
| API Key | AES-256-GCM 加密存库，接口只返回掩码 | 满足「保存在服务器」且不泄露 |
| 雪花 ID | 服务端唯一生成函数 + 客户端「ID 池」按批领取；导入数据由服务端统一重编号 | 前端同步建 ID 的代码几乎不改，服务端保证唯一 |
| 导入导出 | 保留官方 v3 ZIP 格式与前端解析/组装代码，`db` 层改为服务端暂存接口 | 格式 100% 兼容，导入覆盖在数据库事务内原子完成 |
| 管理后台 | 根目录 `admin/` 服务端渲染，复用 `users` 表与雪花 ID | 无额外框架，部署简单，功能完整 |
| 依赖 | 零 Composer 依赖，手写轻量路由/DB/HTTP 封装 | 部署简单，代码可控 |

### 4.2 结构原则

## 6. 数据库设计

统一约定：主键/外键 ID 均为 `BIGINT UNSIGNED`（雪花），时间戳 `BIGINT`（毫秒）。字符集 `utf8mb4`，引擎 InnoDB。

### 6.1 表清单

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `users` | `id`(PK,雪花)、`username`唯一、`password_hash`、`role`(user/admin)、`status`(1/0)、`api_key_enc`、`api_key_mask`、`created_ms`、`updated_ms`、`last_login_ms` | 账号；API Key 加密存储 |
| `auth_tokens` | `id`(PK,雪花)、`user_id`、`token_hash`唯一、`created_ms`、`expires_ms`、`last_used_ms`、`ip`、`ua` | 登录令牌（Cookie），可多端 |
| `sessions` | `id`(PK,雪花)、`user_id`、`title`、`root_message_id`、`messages_count`、`input_tokens`、`output_tokens`、`data`(LONGTEXT)、`created_ms`、`updated_ms` | 会话；`data` 为官方 `Session` JSON（消息 ID 为雪花） |
| `session_files` | `session_id`、`file_id`、`user_id`，PK(`session_id`,`file_id`) | 会话引用附件索引，删除会话时清理无引用原件 |
| `files` | `id`(VARCHAR 64,PK)、`user_id`、`name`、`size`、`is_image`、`mime_type`、`server_id`、`image_size_checked`、`created_ms` | 附件元数据；原件在磁盘 |
| `staging_sessions` | 与 `sessions` 同构 | 导入暂存区 |
| `staging_files` | 与 `files` 同构 | 导入暂存区 |
| `id_sequence` | `id`=1、`last_ms`、`last_seq` | 雪花状态持久化，防重启重复 |
| `login_attempts` | `username`、`ip`、`attempts`、`window_start_ms` | 登录限流（5 次/10 分钟） |
| `admin_logs` | `id`(PK,雪花)、`admin_id`、`action`、`target_type`、`target_id`、`detail`(TEXT)、`ip`、`created_ms` | 管理后台操作审计 |
| `site_settings` | `k`(PK)、`v` | 注册开关、API Base URL、站点名、公告、上传限制等 |

### 6.2 关键约束与索引

- `sessions`：`INDEX(user_id, updated_ms DESC)`，列表按更新时间倒序；统计列由服务端保存时计算。
- `files`：`INDEX(user_id)`；`sessions`：`INDEX(created_ms)`、`INDEX(updated_ms)` 供后台趋势统计。
- `auth_tokens`：`INDEX(user_id)`、`INDEX(expires_ms)`。
- `admin_logs`：`INDEX(admin_id, created_ms)`、`INDEX(created_ms)`。
- `staging_*`：均带 `user_id`，按用户隔离。
- 所有业务查询强制 `user_id = 当前用户`，杜绝越权。

### 6.3 会话 JSON 的选择

`data` 字段直接保存前端官方 `Session` 对象（`id/title/createdAt/updatedAt/messages/rootMessageId`）。原因：

- 与官方 `db.saveSession` 完全同构，前端只需把 IndexedDB 换成 HTTP。
- 分支（`parentId/selectedChildId`）、思考块、工具块、引用、用量等复杂结构无需拆表。
- 消息 ID 在 JSON 内仍是雪花；导出时官方代码会按树重新编号为 1..n。
- 服务端保存时解析 JSON，计算 `messages_count/input_tokens/output_tokens` 供后台统计，不改变原结构。

## 7. 雪花 ID 方案

### 7.1 结构

标准 64 位：`1 位符号 | 41 位毫秒时间戳（自定义纪元 2024-01-01） | 10 位 workerId | 12 位序列号`。

- `workerId`：安装时随机生成 0–1023 写入 `config/config.php`，单机部署足够。
- 时钟回拨：若当前时间小于 `last_ms`，等待至追平（最多 5ms × N），不做取巧。
- 唯一性保障：`Snowflake::nextBatch($n)` 在数据库事务中对 `id_sequence` 行 `SELECT ... FOR UPDATE`，更新 `last_ms/last_seq` 后提交；进程、并发、重启均不会重复。
- **全站唯一入口**：`app/Support/Snowflake.php`；用户、会话、消息、令牌、管理日志全部调用它。

### 7.2 客户端同步 ID 的解决：ID 池

前端官方代码大量同步调用 `createId()`（新建会话、提问、回答、分支）。改造方式：

1. 新增 `frontend/src/services/ids.ts`：登录后预取 200 个雪花（`POST /api/ids {count}`），存入内存池；剩余 < 50 时后台再取 200。
2. `frontend/src/utils/id.ts` 的 `createId()` 从池中按顺序弹出，签名保持同步；池空时由发送入口明确失败提示，绝不生成伪 ID。
3. 服务端按批下发，批次互不重叠；多标签页各自持有独立批次，不会冲突。

### 7.3 导入数据的重编号

官方归档中会话 ID 是 UUID、消息 ID 是会话内自增数字，不满足「全部雪花」。因此：

- 前端仍用官方 `toLocalSession` 解析并暂存（保持格式校验/分支还原逻辑不变）。
- `POST /api/history/staging/commit` 时，服务端在事务内对每个暂存会话：
  1. 会话 ID → 新雪花；
  2. 消息按「父节点优先」拓扑排序，逐条分配新雪花，同步重写 `id/parentId/selectedChildId/rootMessageId`；
  3. 写入正式表并返回新的会话摘要列表。
- 前端 `commitStaging` 直接使用返回的摘要刷新列表，无需二次请求。

## 8. 后端 API 设计

统一前缀 `/api`，JSON 请求/响应；写操作要求 `X-CSRF-Token`；未登录 401；越权 404。

### 8.1 公共与认证

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/site` | 站点公开信息：名称、是否开放注册、公告 |
| POST | `/api/auth/register` | 注册（受 `site_settings.allow_register` 控制） |
| POST | `/api/auth/login` | 登录，下发 HttpOnly Cookie 令牌 + CSRF Token |
| POST | `/api/auth/logout` | 注销当前令牌 |
| GET | `/api/auth/me` | 当前用户、角色、`has_api_key`、`api_key_mask`、CSRF |
| POST | `/api/account/password` | 修改密码（校验旧密码，吊销其他令牌） |
| POST | `/api/account/api-key` | 校验（GET `/models`）通过后加密保存，返回掩码 |
| DELETE | `/api/account/api-key` | 清除 API Key |
| GET | `/api/account/balance` | 代理 `GET /user/balance`，设置页展示余额 |

### 8.2 ID 与聊天数据

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/ids` | 批量分配雪花（`count` ≤ 1000） |
| GET | `/api/sessions` | 会话摘要列表 |
| GET | `/api/sessions/{id}` | 单个会话完整 JSON |
| PUT | `/api/sessions/{id}` | 保存会话（整体覆盖），同步附件引用与统计 |
| PATCH | `/api/sessions/{id}` | 重命名 |
| DELETE | `/api/sessions/{id}` | 删除会话及无引用附件 |

### 8.3 附件

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| PUT | `/api/files/{id}` | 原始字节上传（`application/octet-stream`），落盘 + 元数据入库 |
| GET | `/api/files/{id}` | 鉴权后返回原件（缩略图/查看/导出用） |

### 8.4 历史导入暂存（对应官方 db 暂存接口）

| 方法 | 路径 | 对应官方函数 |

### 8.5 DeepSeek 代理（全部使用当前用户 Key）

| 方法 | 路径 | 上游 |
| --- | --- | --- |
| POST | `/api/deepseek/messages` | `/anthropic/v1/messages`，SSE 透传 |
| POST | `/api/deepseek/files` | `/anthropic/v1/files`（multipart 转发，含 `anthropic-beta`） |

## 9. 聊天请求全链路

```text
1. 用户在 ChatInput 提交
2. store.sendMessage：从 ID 池取 session/message ID，写入内存并 persist
3. streamReply：按官方逻辑补齐附件 serverId（经 /api/deepseek/files 上传）
4. POST /api/deepseek/messages（官方请求体：
   model / system / messages / thinking / safety_check / tools / title）
5. PHP：读取用户 Key → cURL 流式请求 api.deepseek.com → 逐块 echo + flush
6. 浏览器按官方 sse.ts 解析事件，applyEvent 累积 blocks
7. 收到 message_delta.title 时自动写标题（官方逻辑）
8. 结束/停止/出错后 persist → PUT /api/sessions/{id} 落库
9. visibilitychange/pagehide 时官方 bindChatPersistence 再兜底保存
```

要点：

- 浏览器不再直连 DeepSeek，也不持有 API Key。
- 请求体完全沿用官方 `CreateMessageRequest`，因此深度思考、联网搜索、链接阅读、标题、`latest_reminder`、`safety_check` 全部保留。
- PHP 侧关闭输出缓冲，设置 `X-Accel-Buffering: no` 与 `Content-Type: text/event-stream`；Nginx 配置 `fastcgi_buffering off; proxy_buffering off;`。
- 客户端中断（停止生成/关页）时 `connection_aborted()` 检出并关闭 cURL，避免继续消耗额度。

## 11. 账号与安全设计

1. **密码**：`password_hash(PASSWORD_DEFAULT)`；长度 ≥ 8；修改密码需旧密码；修改后吊销其他登录令牌。
2. **登录态**：32 字节随机令牌，`sha256` 入库；Cookie `ds_token`，`HttpOnly`、`SameSite=Lax`、HTTPS 下 `Secure`；有效期 30 天，滑动续期。
3. **CSRF**：登录后下发 `csrf`，所有非 GET 请求校验 `X-CSRF-Token` 与 `Origin`。
4. **API Key**：AES-256-GCM，密钥来自 `config/config.php` 的 `app_key`（安装时随机 32 字节）；只在代理请求瞬间解密；界面仅显示 `sk-****xxxx`。
5. **越权**：所有资源查询带 `user_id`；后台独立 `role=admin` 校验；禁用用户立即吊销令牌。
6. **限流**：登录失败 5 次/10 分钟（`login_attempts`）；代理接口对单用户做并发限制（同时 3 个流）。
7. **上传**：沿用官方扩展名白名单与 64MB/32MB 限制；服务端再次校验扩展名、大小、图片真实性；磁盘路径只用附件 ID。
8. **日志**：只记录请求 ID、状态、耗时、用户 ID；绝不记录 API Key、消息正文；后台操作写 `admin_logs`。
9. **安装安全**：`config/config.php` 位于 Web 拒绝目录；安装完成后写 `config/installed.lock`，`install.php` 拒绝重复安装。

## 12. 历史导入导出

### 12.1 格式

完全遵循官方 `export_format_version: 3`：

```text
manifest.json
chat_sessions/{session_id}.json
chat_session_index.json
chat_sessions/{session_id}_files/{file_id}_{file_name}
```

支持官方 ZIP32 的 STORE/DEFLATE；ZIP64、加密、分卷不支持（与官方一致）。

### 12.2 导入（彻底覆盖）

1. 前端官方逻辑：`checkArchiveFormat` → 用户确认 → `importHistory`。
2. `importArchive` 逐条解析、校验、`toLocalSession` 转换（保留官方全部规则：消息树、分支、模板、思考、工具、图片身份）。
3. 暂存接口把会话 JSON 与图片原件写入服务端暂存区（`staging_*` + `storage/staging/{user_id}`）。
4. `commit` 在**单个 MySQL 事务**中：
   - 清空该用户 `sessions / session_files / files`；
   - 把暂存会话重编号为雪花后写入；
   - 把暂存文件移入 `storage/uploads/{user_id}` 并写入 `files`；
   - 清空暂存表；任何一步失败整体回滚，原数据不变。
5. 返回新摘要列表，前端刷新为导入结果并回到新对话。

### 12.3 导出

复用官方 `exportArchive` 与 `toArchive`：前端从 `db.loadSession` / `db.loadFile`（已改为服务端接口）读取全部会话与图片原件，ZIP 在前端组装下载。文件名保持 `deepseek_data-日期.zip`。

### 12.4 删除全部对话

官方 `clearHistory` 走「空暂存 + commit」，服务端在同一事务内清空会话、附件索引与原件，保留账号、API Key 和本地设置。

## 16. 构建与部署

### 16.1 构建

```bash
cd frontend && pnpm install && pnpm build
# 输出：/index.html、/static/**
```

- rspack 输出根目录 `index.html` 与 `static/**`（`clean:false`，避免删除 PHP 文件）。
- `publicPath: '/'`，带 contenthash。
- 构建产物提交仓库，确保克隆后即可部署。

### 16.2 Nginx（示例）

```nginx
server {
    root /var/www/deepseek;          # 项目根目录
    index index.html;
    client_max_body_size 64m;

    # 后端 API
    location /api/ { try_files "" /index.php$is_args$args; fastcgi_buffering off; }

    # 管理后台
    location /admin/ { try_files $uri /admin/index.php$is_args$args; }

    # SPA
    location / { try_files $uri $uri/ /index.html; }

    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_read_timeout 300s;
    }

    # 内部目录与杂物一律拒绝
    location ~ ^/(app|config|storage|database|docs|deploy|frontend|scripts)/ { deny all; }
    location ~ ^/\.(git|gitignore) { deny all; }
}
```

### 16.3 Apache

- 根目录 `.htaccess`：`/api` 重写到 `index.php`，SPA 回退 `index.html`；`app|config|storage|database|docs|deploy|frontend|scripts` 目录 `Require all denied`。
- 提供 `deploy/apache-vhost.conf.example`。

### 16.4 开发模式

```bash
# 后端
php -S 127.0.0.1:8080 -t . router.php

# 前端（rspack dev server，8090，代理 /api 与 /admin 到 8080）
cd frontend && pnpm dev
```

> `router.php` 仅用于 PHP 内置服务器：静态文件直接返回，`/api/*` 交给 `index.php`，其余回退 `index.html`；生产环境使用 Nginx/Apache 规则。

| 根目录部署导致内部代码被访问 | 源码/配置泄露 | Nginx/Apache 拒绝 `app/config/storage/database/docs/deploy/frontend/scripts`；`.htaccess` 兜底 |
| PHP 输出缓冲导致 SSE 不实时 | 打字机效果失效 | 关闭所有缓冲、`X-Accel-Buffering: no`、Nginx `fastcgi_buffering off` |
| 上游需要官方 Key 才能联调 | 无法真实测试 | 用临时 mock SSE 服务验证代理；真实 Key 由用户提供后验收 |
| 大 ZIP 导入内存/超时 | 导入失败 | ZipArchive 落盘解析、分批写暂存、事务提交；限制单次包大小并在 README 说明 |
| 明文 Key 泄露 | 严重 | 加密存储、掩码返回、日志脱敏、代理即时解密 |
| ID 池耗尽 | 发送失败 | 预取 200/阈值 50 自动补；池空时明确提示而非伪造 ID |
| 管理后台误操作 | 数据丢失 | 危险操作二次确认、操作日志、至少保留 1 名管理员、禁用即吊销令牌 |
| `scripts/` 误提交 | 仓库臃肿/泄露参考代码 | 根 `.gitignore` 忽略 `/scripts/`；提交前 `git status` 核查 |
| 官方接口扩展权限差异 | 搜索/标题不可用 | 关闭时前端已有降级展示；README 注明需支持扩展的 Key |
| 许可证合规 | 法律风险 | 保留官方 MIT LICENSE 与版权声明，README 注明来源 |
